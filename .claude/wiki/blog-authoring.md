# Wiki · 게시글(.mdx) 작성 규칙

기술 블로그 글(`blog/*.mdx`) 작성 시 지켜야 할 상세 규칙. 절차는 [blog-post 스킬](../skills/blog-post/SKILL.md) 참고.
(사이트는 Docusaurus 기반. 블로그는 `blog/`, 주제별 문서는 `docs/`.)

## 1) 파일 / 프론트매터
- 파일명: `blog/YYYY-MM-DD-slug.mdx`. 날짜가 목록 정렬 순서를 결정한다.
- **날짜는 실제 작성일(=오늘)로 쓴다 — 미래 날짜 금지.** 목록에서 위로 올리려고 날짜를 앞당겨(미래로) 잡지 않는다. 파일명 날짜와 프론트매터 `date`를 모두 오늘로 맞춘다.
  - **"오늘"은 항상 PC 시스템 시간으로 확인한다** — `date "+%Y-%m-%d"` 셸 명령으로 읽는다. 대화 컨텍스트에 주어진 날짜(환경 프롬프트의 `currentDate` 등)는 실제와 다를 수 있으니 신뢰하지 말고, 반드시 `date` 명령 결과를 기준으로 파일명·`date`를 정한다.
  - **같은 날 여러 글**이면 프론트매터 `date`에 **시각까지** 넣어 순서를 정한다(같은 날이면 시각이 늦은 글이 위로). 파일명 날짜는 동일해도 된다.
    - **반드시 KST 오프셋 `+09:00`을 붙인다**: `date: 2026-09-23T15:00:00+09:00`. 오프셋 없이 `T15:00:00`만 쓰면 **UTC로 해석**돼, 15:00~23:59는 KST(+9) 화면에서 **다음 날로 표시**된다(실제로 09-23 글이 09-24로 보이는 사고가 있었음).
  - **참조 순서**: 다른 글을 링크로 참조하면, 참조하는 글이 목록에서 위(더 최신 시각)에 오도록 시각으로 조정한다.
- frontmatter:
  - `slug`: URL 슬러그(kebab-case, 파일명 슬러그와 동일하게).
  - `title`: 제목. 콜론(`:`) 등 특수문자가 있으면 큰따옴표로 감싼다.
  - `authors: [ johnycho ]` — 저자는 `blog/authors.yml`에 등록된 것만. 현재 `johnycho` 하나.
  - `tags: [ ... ]` — `blog/tags.yml`에 정의된 태그만 사용(7절).
  - `description`: **(권장·SEO)** 검색 결과·소셜 카드에 노출될 1~2문장 요약. **약 150자 이내**로 글의 주제와 **핵심 키워드**를 담는다. 생략하면 truncate 앞 본문에서 자동 추출되지만, 직접 쓰면 노출 문구 품질이 올라간다.
  - `image`: (선택·SEO) 소셜 공유(OG) 대표 이미지 경로(`/img/...`). 생략하면 사이트 기본 카드(`img/social-card.jpg`)를 쓴다.
  - `keywords`: (선택·SEO) 글 고유 키워드 배열. 태그로 충분하면 생략.
  - **참고**: 게시글 페이지에는 `BlogPosting` 구조화 데이터(JSON-LD: 제목·날짜·저자·태그·대표 이미지·URL)가 **자동 주입**된다(`src/theme/BlogPostItem`). 사이트 전역 `WebSite`/`Person` JSON-LD·사이트맵·기본 메타(description/keywords/robots)는 [`docusaurus.config.ts`](../../docusaurus.config.ts)에서 관리하므로 글에서 따로 넣지 않는다.
- 프론트매터 바로 다음: `<!-- truncate -->` → (빈 줄) → 본문. truncate가 목록 카드의 요약 경계.
  - **본문 첫머리에 `<br /><br />` 등 여백을 넣지 않는다** — 글 맨 위에 빈 줄이 생겨 어색하다. truncate 다음 빈 줄 하나 두고 바로 인트로 문단으로 시작.
  - `@site/...` 컴포넌트를 쓰면 `import` 문은 프론트매터와 `<!-- truncate -->` 사이(맨 위)에 둔다.

## 2) 본문 규칙
- **눈높이: 초보자도 이해할 수 있게 쓴다.** 전문 용어(예: MDC, ECS, grok, FQCN)는 처음 나올 때 한 줄로 풀어 준다. 필요하면 비유를 쓰고(예: 컨텍스트=세트/창고), 짧은 문장으로 단계를 밟는다. 배경 지식을 가정하지 말고 "왜 필요한지"부터 설명한다. 용어가 많으면 글 끝에 "용어 한 줄 정리" 표를 붙여도 좋다.
- **개념·단계 설명에는 구체적 상황 예시를 곁들인다.** "언제 이게 필요한가"를 실제 시나리오(예: 동시 접속 급증, 특정 쿼리 반복)로 먼저 보여주면 이해가 쉽다. 추상적으로만 설명해 감이 안 잡히면, 구체적 숫자(예: `50 이벤트 × 5,000명 = 250,000 요청/초`)와 의사코드로 "어떻게 동작하는지"까지 보여준다.
- **텍스트와 설명만으로 채우지 않는다 — 시각 자료와 실무 예시를 반드시 넣는다.** 설명 문단과 표만 이어지면 독자가 내용을 체감하기 어렵다(실제 피드백: "너무 설명만 있어서 잘 와닿지 않는다").
  - **흐름·절차·비교가 나오는 섹션마다 그림을 우선 검토한다.** 단계 흐름은 "누가 무엇을 하는지" 스윔레인, 선택 기준은 흐름도, 시간에 따른 차이는 타임라인, 구조는 C4/PlantUML로 그린다(방식은 4절). 같은 내용을 표로만 나열하지 말고 **그림을 먼저, 상세 표는 그 뒤에** 둔다.
  - **도구·기법·개념 소개 글에는 "실무 적용 예시" 섹션을 둔다.** 실제 상황(무엇이 문제인가) → 진행(실제 명령, 프롬프트, 코드) → 결과(사람이 쓰는 시간, 달라지는 점)를 구체적으로 보여 준다. 예시 수치나 시간이 가정이면 가정이라고 밝힌다.
  - **기준**: 텍스트만 이어지는 구간이 화면 두세 개 분량을 넘으면 그림, 코드 예시, 시나리오 중 한 가지를 넣는다. 섹션 대부분이 문단과 표뿐이면 리뷰에서 지적한다.
- **외부 발표·영상·아티클을 기반으로 쓸 때는 그 자료가 강조한 핵심 기법을 빠짐없이 반영한다.** 제목만 보고 일반론으로 채우지 말고, **공식 세션 페이지·발표사 기술블로그·원문**으로 실제 다룬 기법(예: 무효화에 쓴 메시지 큐 종류, 워밍업, 트랜잭션 경계 등)을 교차 확인한다. 자막을 그대로 옮기지는 않되(저작권), 다룬 주제·기법은 누락 없이 내 언어로 정리하고 인트로에 원문을 링크로 출처 표기한다. 확인이 안 되면 추측해 단정하지 말고 범위를 좁힌다.
- **인용·근거는 주장을 정확히 뒷받침하는 것만 쓴다.** 어떤 주장(예: "커서는 별도 커넥션을 쓴다")에 인용을 붙일 때, 그 인용문이 그 주장을 **직접** 뒷받침하는지 확인한다. 공식 문서에 그 내용이 없으면 **추론을 인용처럼 포장하지 말고**, 프레임워크·라이브러리 **소스 코드에서 근거를 찾아** 코드 인용(핵심 몇 줄만 발췌 + `...`로 생략 + 파일 링크)으로 제시한다. 인용·코드 바로 아래에는 **한 줄 해석(`→ …`)** 을 붙여 그게 무엇을 뜻하는지 풀어 준다. 주장마다 근거를 따로 붙이고, 여러 인용을 뭉뚱그리지 않는다. (짧은 발췌만, 저작권 주의)
- **판단 과정을 독자가 따라오게 쓴다.** ① 여러 후보 중 하나를 고른 글이면, 각 후보를 기준에 하나씩 대입해 "어디서 왜 탈락하는지"를 단계별로 보여주고 요약 표는 그 뒤에 둔다. ② 앞 섹션을 번호로 참조할 때("제약 2의 규칙")는 그 내용을 괄호로 한 번 더 적어(`제약 2의 규칙(한 번에 읽는 개수 = 커밋 간격)`) 독자가 되짚지 않게 한다. ③ 설명 뒤 자연히 떠오를 반론·의문(예: "그 옵션만 켜면 되지 않나?")을 예상해 바로 짚어 답한다. ④ 규칙·트레이드오프·타임라인은 말로만 두지 말고 **예시 코드나 시퀀스 다이어그램**으로 보여준다(ASCII 타임라인 금지). 다이어그램은 4절 우선순위대로 **PlantUML 우선, Mermaid는 최후**다 — 시퀀스도 PlantUML로 그린다([diagram-static](../skills/diagram-static/SKILL.md)). (git 커밋 그래프처럼 PlantUML로 안 되는 것만 Mermaid.)
- **표현·단어·문장 규칙은 [`blog-polishing` 스킬](../skills/blog-polishing/SKILL.md)로 다듬는다** — 지양어(단어)·문체(존댓말 통일)·톤(담백)·모호한 정성 표현·모순 관점·문장 조각/명사화·섹션 제목·근거 링크 정밀도·보충 노트·주체·나열식·표방향 등. 규칙 원본과 "검사 방법"은 그 스킬이 SSOT로 관리한다(작성·수정·리뷰 시 필수 실행).
- **코드 예시의 메서드 체이닝**은 fluent 정렬을 따른다(첫 줄 마지막 호출의 `.` 아래로 세로 정렬). 상세·예시는 [common-authoring.md](./common-authoring.md) 참고.
- **제목 H1(`# ...`)을 본문 맨 앞에 중복으로 넣지 않는다** — 제목은 프론트매터에 있다. 인트로 문단으로 시작.
- 원본 초안(예: `~/Downloads/*.md`)을 반영할 때는 맨 앞 H1 한 줄만 제거하고 나머지 본문·코드블록은 그대로 살린다.
- 섹션 구분은 `##`부터 사용. 줄바꿈은 `<br />`.
- **글 안의 번호 붙은 항목을 언급하면 해당 섹션으로 링크한다.** "케이스 2", "제약 1", "사례 3"처럼 같은 글의 번호 섹션을 본문에서 가리킬 때는 `[케이스 2](#케이스-2--힙-outofmemoryerror)`처럼 앵커 링크를 건다. 앵커는 제목에서 자동 생성되므로 `npm run build` 후 `build/blog/<slug>.html`의 `id="…"`로 실제 값을 확인한다. 그림 속 번호는 클릭할 수 없으니 본문 문장에서 링크한다.
  - **단, 바로 아래에 이어지는 섹션 목록을 링크로 다시 나열하지 않는다**("각 케이스로 바로 이동: 케이스 1, 케이스 2, …" 같은 문장). 목차와 본문이 이미 같은 역할을 하므로 중복이다.
- **상호 참조 링크(blog ↔ blog, blog ↔ wiki)**: 다루는 개념이 다른 글/문서에 이미 정리돼 있으면, 그 대목에서 **관련 글·wiki 문서로 링크를 건다.** 개념의 기초·상세는 wiki(`wiki/*` → URL `/wiki/*`)로 넘기고 본문은 핵심에 집중하면 중복 서술이 줄고 탐색이 쉬워진다. 반대로 wiki 문서에서도 심화·사례 글이 있으면 blog로 링크할 수 있다.
  - **단, 밀접하게 연관된 것만.** 각 대목에서 정말 직접 관련된 대상 1개 정도만 링크하고, 느슨하게 관련된 것을 여러 개 나열하지 않는다(링크 남발은 오히려 산만).
  - **wiki 링크 URL은 폴더 경로를 포함한다.** wiki 문서의 `slug`는 폴더 기준 **상대경로**라, 예컨대 `wiki/computer-science/cs-jwt.md`(`slug: cs-jwt`)의 실제 URL은 `/wiki/cs-jwt`가 아니라 `/wiki/computer-science/cs-jwt`이다. 빌드가 깨진 링크를 잡아내니(`onBrokenLinks`), `npm run build`로 반드시 확인한다.
- **`<mark>` 하이라이트 적극 활용**: 각 섹션에서 **가장 핵심이 되는 한 문장/구절**을 `<mark>...</mark>`로 강조한다. 독자가 스크롤하며 요점만 훑어도 흐름을 잡을 수 있게 한다.
  - 기준: 섹션당 대략 1개(많아야 2개). 정의·결론·핵심 규칙처럼 "이것만 기억하면 되는" 부분에.
  - 남용 금지: 여러 문장을 통째로 칠하거나 한 섹션에 여러 개 칠하면 강조 효과가 사라진다. 이미 `**볼드**`나 `>` 인용구로 강조된 블록과 중복해 덧칠하지 않는다.
  - `<mark>` 안에 `**볼드**`·인라인코드·따옴표를 포함해도 된다. 코드블록 안에서는 쓰지 않는다.

## 3) MDX(v3) 주의 — 렌더 깨짐 방지
- 코드블록(``` ```) **밖** 본문에서 raw `{` `}` `<태그` 는 JSX로 해석되어 빌드가 깨질 수 있다.
  - 의도한 `<mark>`, `<br />`, `<!-- -->` 는 예외(그대로 사용).
  - 그 외 `<`, `{`, `}` 가 본문 텍스트에 필요하면 이스케이프(`&lt;`, `&#123;`, `&#125;`).
- 제네릭(`List<Long>`), ASCII 다이어그램, 중괄호 등은 **코드블록 안에서는 안전** — 그대로 둔다.
- **`**볼드**`가 구두점·기호로 끝나고 뒤에 한글이 공백 없이 붙으면 렌더되지 않는다** — 닫는 `**` 바로 앞이 `)`·`]`·`'`·`"`(닫는 따옴표)·**`+`·`%`·`>`·`-` 등 기호**이고 그 다음이 공백 없이 한글(조사)이면(예: `**복제본(read replica)**을`, `**"무상태를 조금 포기"**하는`, `**JDK 24+**라면`, `**99%**까지`), CommonMark 규칙상 강조가 닫히지 않아 `**`가 그대로 보인다.
  - **해결: 구두점·기호는 그대로 볼드 안에 두고, 닫는 `**` 뒤에 한 칸 띄우거나 표현을 재구성한다** — 볼드 뒤에 공백이 오면 강조가 정상적으로 닫혀 적용된다. 예: `**복제본(read replica)** 을`, `**무상태(stateless)** 여야`. 기호로 끝나 어색하면 재구성: `**JDK 24+**라면` → `**JDK 24 이상**이라면`, `**3.2+**는` → `**3.2 이상**은`. (볼드 밖으로 글로스를 빼내지 말 것.)
  - **검사**: `grep -rnoE '[+%>)\]"'"'"'][*][*][가-힣]' blog/` 로 닫는 `**` 앞 기호+뒤 한글 패턴을 훑는다(여는 볼드 오탐은 제외).
- **물결표(`~`) 숫자 범위가 취소선으로 렌더된다** — 한 줄(코드블록 밖)에 `~`가 **2개 이상**이면 GFM이 그 사이를 ~~취소선~~으로 해석한다(예: `30~60% … 1~2개 … 6~7` → 중간이 줄 그어짐, `20~200μs | 수백~수천` 표 셀도 동일). 한 줄에 1개면 안전하다.
  - **해결: 범위의 `~`를 `\~`로 이스케이프**한다(렌더는 그대로 `~`). 예: `30\~60%`, `수백\~수천`, `발주\~입고\~정산`. (코드블록·인라인코드 안 `~`는 그대로 둔다.)
  - **검사**: 코드펜스 밖에서 한 줄 `~` 2개 이상(인라인코드 제외)을 훑는다. 종종 반복되는 함정이니 발행 전 확인.
- 작성 후 코드블록 밖 본문에 위험 패턴이 없는지 스캔한다(스킬 6절).

## 4) 다이어그램·시각화 — 방식 선택 후 해당 스킬로

네 가지 방식이 있다. **대상에 맞게 골라 해당 스킬의 절차를 따른다**(상세는 각 스킬 문서).

| 대상 | 방식 | 스킬 |
|---|---|---|
| **모든 그림** — 구조, 시퀀스, 흐름(판단, 액티비티), 상태, 인프라, ER, C4 표기, git 그래프, 정적 차트, 축/타임라인, 공간 배치형 | `<rect>`, `<text>` 좌표를 **손수 배치한 정적 SVG**(폭 440px 안팎, 본문 색인, 선명) | [diagram-svg](../skills/diagram-svg/SKILL.md) — **유일한 방식** |
| 지표·추이·분포가 "움직임"으로 의미 있는 애니메이션 | 직접 만든 Canvas 애니메이션 컴포넌트(MonitorCharts) | [chart-canvas](../skills/chart-canvas/SKILL.md) |
| (예외, 사용자 승인 글만) 현실의 물건 이동을 보여 주는 인터랙티브 등각 모형 | `static/diagrams/<이름>(-light).html`을 `<AnatomyEmbed>`로 삽입 | anatomy 스킬(`~/.claude/skills/anatomy`), 빌드 `tools/anatomy/<이름>/build.mjs` |
| (보관, 미사용) PlantUML, C4-PlantUML, Mermaid / archify 인터랙티브 | — | [diagram-static](../skills/diagram-static/SKILL.md), [diagram-archify](../skills/diagram-archify/SKILL.md) — **보관용**. 쓰지 않는다 |

- **그림은 손수 SVG만 쓴다. PlantUML, C4-PlantUML, Mermaid, archify는 쓰지 않는다.** 블로그의 그림 약 190개를 손수 SVG로 옮기면서 표현하지 못한 그림이 없었다. 스킬과 컴포넌트(`ArchifyEmbed`)는 언젠가 필요할 수 있어 삭제하지 않고 보관한다. `scan-polishing.py`가 ` ```plantuml `, ` ```mermaid `, `<ArchifyEmbed`를 지적하므로, 보관 방식을 꼭 써야 하는 글(예: C4 모델 글의 C4-PlantUML 코드 예시)만 사유와 함께 `--allow`로 예외 등록한다.
- **anatomy 인터랙티브 모형은 예외로만 쓴다.** 손수 SVG가 기본이고, anatomy는 현실의 물건 이동을 모형으로 보여 주면 이해가 크게 쉬워지는 글에서 기존 SVG를 **보완**할 때만 쓴다(현재 SCM 글). `scan-polishing.py`가 `<AnatomyEmbed`를 `그림형식`으로 지적하므로, 새 글에 쓰려면 사용자 확인 후 `--allow`로 예외 등록한다. 그림 문구(제목, readout, 범례, 캡션)도 지양어 검사 대상이다(`static/diagrams/*.html`). 다크와 라이트 두 테마(`--light`)를 모두 빌드하고 390px 폭에서 읽히는지 확인한다.
  - **색**: 블로그 팔레트의 연한 파스텔을 쓴다(강조 구역 윗면 파랑 `#D3E0F8`, 초록 `#CDEBD1`, 분홍 `#F8D3DF`, 주황 `#FBE6B8`, 청록 `#CBEDF1`, 옆면과 선은 한 단계씩 진하게). 건물 회색은 밝게(윗면 `#F4F4F2`) 하고, 너무 짙거나 무채색이면 안 된다.
  - **강조**: 지금 단계의 구역은 진한 테두리와 은은한 발광으로 첫눈에 보이게 하고, 나머지는 원래 색을 옅게 남긴 톤으로 낮춘다(완전히 투명하게 하지 않는다). 건물 전체 강조는 검은 선 대신 연한 회청색(`#7D8A99`) 테두리로 한다.
  - **작업자**: 귀여운 2.5~3등신 캐릭터(큰 둥근 머리, 눈, 볼, 미소)로 그리고, 작업복은 컬리 보라(`#5F0080` 계열)로 한다. 층마다 여러 명을 두고, 단계와 상관없이 늘 직무 동작을 한다. 직선으로 왕복하지 않고 여러 지점을 도는 경로로 움직인다(일하는 지점에서만 멈추고, 나머지 지점은 돌아서 지나간다). 카트는 손잡이를 두 손으로 잡고 앞에 두고 민다. 물건은 사람, 카트, 설비가 옮기고 혼자 미끄러지지 않는다.
  - **현장감**: 지게차(노란 차체, 운전자 탑승, 팔레트를 싣고 내리며 후진도 한다), 핸드자키, 노란 안전선, 도크 문 옆 고무 범퍼, 랩 감은 팔레트를 넣는다. 트럭 뒷문은 하차와 상차 동안 열린다.
  - **트럭**: 입고 트럭은 흰 탑차(공급사), 출고 트럭은 컬리 보라 냉장 탑차에 흰 컬리 로고(`static/img/kurly-logo.svg` 원본 그대로)를 붙인다.
  - **둥근 부품**(바퀴, 다이얼, 팬)은 원통과 원으로 그린다. 상자로 대신하지 않는다.
  - **공간이 있는 주제**(물류센터 등)는 층을 위아래로 띄운 분해 단면으로 전체 흐름을 보여 주고, 예시 배치임을 캡션에 밝힌다. 같은 글의 그림은 같은 건물, 카메라(방위각 40, 고도 22), 층 간격(96), 카드 크기(600x720)를 써서 같은 센터로 보이게 하고, 층이 늘어도 세로로 길어지지 않게 층 간격과 랙 높이를 줄인다. 같은 글의 두 번째 그림은 첫 그림 빌드를 그대로 쓰고(모드 인자, 예: `scm-milk-flow/build.mjs --warehouse`), 그 그림이 다루지 않는 설비는 숨기며, 계층 표시줄과 확대창(둥근 창과 지시선)으로 그 그림만의 내용을 드러낸다. 두 그림이 서로 구분돼야 한다.
  - **그림 문구**는 `build.mjs`의 `TEXT` 한 곳에 모으고 간단명료하게 쓴다. readout은 "층 장소, 지금 일어나는 일", 범례는 "이름(색): 짧은 구", 캡션은 핵심 한두 문장으로 쓴다.
  - **iframe 배경**: 글 배경과 이어지도록 페이지 배경을 투명하게 하고 `html`의 `color-scheme`을 테마별로 강제한다(`AnatomyEmbed`가 iframe의 `color-scheme`을 사이트 테마에 맞춘다. 둘이 다르면 브라우저가 불투명 배경을 칠한다).
- **ASCII 그림 금지 — 박스 문자 그림과 디렉터리 트리도 SVG로.** `┌─┐`, `│`, `▼`, `──▶` 같은 문자로 그린 구조도, 흐름도, 영수증 같은 예시, `├──`로 그린 디렉터리 트리는 코드블록 안에 두지 않고 SVG로 그린다(트리는 폴더 아이콘, 가이드 선, 역할별 색, 주석을 작은 회색 글자로). 한글이 섞이면 코드블록에서 열 정렬이 깨지고 모바일에서 줄이 넘친다.
- **글 안 ` ```svg ` 블록과 `static/img/c4/*.svg` 파일은 항상 같아야 한다.** 그림 문구를 고칠 때는 둘을 함께 고친다. 스캐너는 블록의 글자를 검사하고 독자는 파일을 보므로, 한쪽만 고치면 지양어가 그림에 남는다. `scan-polishing.py`가 다르면 `그림불일치`로 지적한다.
- **그림 안 텍스트도 단어, 문장 규칙 대상이다.** 라벨, 제목, 범례, alt에도 지양어와 구어("꽉 찬", "손볼 곳", "번지는", "옆 기능", "응답이 튐", "장애가 났을 때", "보너스")를 쓰지 않는다. `scan-polishing.py`가 ` ```svg ` 코드블록의 `<text>` 내용과 ` ```plantuml ` 코드블록(C4-PlantUML 포함)의 라벨(따옴표 문자열, 화살표와 note의 `:` 뒤, title, 여러 줄 note, 액티비티, 조건), ` ```mermaid ` 코드블록의 노드, 간선, subgraph 라벨, `static/diagrams/*.html`의 글자도 검사한다. 분기 라벨은 `Y` / `N`.
- **그림에는 본문에 있는 내용만 담는다.** 본문에 없는 수치나 이름(예: 메모리 크기, 패턴 이름)을 그림에만 넣지 않는다. 꼭 필요하면 본문에도 근거와 함께 쓴다.
- **손수 SVG를 쓰는 이유.** PlantUML 자동 레이아웃은 가로로 길게 펼쳐져 본문 폭에서 줄어들면 글자를 읽기 어렵고, 소스만 고치고 다시 렌더하지 않으면 그림이 소스와 달라진다. 손수 SVG는 폭 440px 안팎에 맞춰 배치를 직접 정하고, 소스와 그림이 같은 파일이라 어긋나지 않는다.
  - 시퀀스는 참여자를 세로 줄(lifeline)로 두고 메시지를 번호와 함께 위에서 아래로 쌓는다. 참여자가 많아 폭이 모자라면 API 서버처럼 중심이 되는 참여자를 가운데 두고 번호 붙은 화살표와 단계 범례로 그린다.
  - 판단 흐름은 위에서 아래로 질문 상자와 Y/N 분기를 쌓고, 결론 상자를 색으로 구분한다.
- **모바일 폭 점검**: **원리** — 모바일은 이미지를 **화면 폭(아이폰 콘텐츠 영역 ~350~360px)에 맞춰 축소**한다(`max-width:100%`). 그래서 **SVG가 넓을수록 더 많이 축소돼 글자가 작아진다**(= 깨져 보임). 역으로 **SVG 폭을 ~360px 이하로 두면 축소 없이 원본 크기**로 보여 가장 선명하다. **폭을 늘리는 건 모바일에 도움이 안 된다**(데스크톱만 커지고 모바일은 더 나빠짐).
  - **목표 폭**: **이상적 ~360px, 실용 안전 상한 ~440px, 최대 520px.** 넘으면 모바일에서 축소돼 글자가 작아진다. 손수 SVG는 루트 `width`로 확인한다.
  - **줄이는 법**: 긴 라벨은 두 줄로, 가로 흐름은 세로 배치로, 요소가 많으면 그림을 두 개로 나눈다. **내용 삭제보다 줄바꿈, 배치 변경, 분리를 먼저.**
- **설명 노트는 대상보다 먼저(위에) 둔다** — 시퀀스/흐름 다이어그램에서 어떤 메시지·단계를 설명하는 노트는 그 동작 **아래가 아니라 위**에 배치한다. 노트(개념)가 먼저 읽히고 → 해당 동작이 이어져야 자연스럽다(예: "① 멱등 프로듀서" 노트를 `send` 화살표 **위**에 둔다).
- **도구 GUI 화면은 "오리지널 목업"으로 재현**한다(스크린샷 복사·핫링크 금지). 재사용 컴포넌트 [`src/components/blog/MatMockup.tsx`](../../src/components/blog/MatMockup.tsx)(MAT 창 목업) 패턴(공통 창틀 + 뷰별 데이터 배열)으로 새 도구 화면을 추가하고, 캡션에 "실제 스크린샷 아님" 명시. 테마는 사이트 변수(`--site-*`), 좁은 화면은 `overflow-x:auto`.
- **저작권(시각자료 공통)**: 다른 글의 이미지·애니메이션이나 도구 스크린샷을 복사/핫링크하지 말 것. 같은 개념·화면은 **직접 구현한 컴포넌트(canvas/목업)로 재현**하고, 원문·도구는 **링크로만** 참조한다.

## 6) 검증
- `npm run build` 로 MDX 컴파일 성공 확인(빌드 실패 시 MDX 파싱 오류 위치가 표시됨).
- 필요 시 `npm start` 로컬 서버로 목록/본문 렌더 확인.
- **작성·수정 후에는 반드시 [`blog-review` 스킬](../skills/blog-review/SKILL.md)(`/blog-review`)를 거친다(커밋 전 필수).** 이 리뷰는 먼저 [`blog-polishing` 스킬](../skills/blog-polishing/SKILL.md)(`/blog-polishing`)로 표현·문체를 **실제로 다듬은 뒤**, 작성·MDX·다이어그램·코드 정렬·인용 정합성까지 검토한다(polishing이 review에 묶여 있어 함께 실행된다).
- **지양어·문장 규칙 대조·수정은 [`blog-polishing` 스킬](../skills/blog-polishing/SKILL.md)이 담당한다**(규칙 표 전체를 매번 대조). 이 스킬을 반드시 실행해 위반을 없앤다.
